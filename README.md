# Transaction Ledger API

Node.js + Express + SQLite (better-sqlite3).

## Run locally

```bash
npm install
npm start          # http://localhost:3000  (PORT and DB_FILE env vars optional)
npm test           # 20 tests
```

Requires Node 18 or newer. If you switch Node versions after `npm install` (for example with nvm) and see
`NODE_MODULE_VERSION` errors, run `npm rebuild better-sqlite3`.

## Project structure

```
src/db.js          schema + constraints + triggers
src/validation.js  checks incoming data
src/ledger.js      business logic (atomic transactions)
src/errors.js      one consistent error shape
src/app.js         routes + error handler
src/server.js      starts the server
tests/             integration tests
```

## API

Errors always look like: `{ "error": { "code": "...", "message": "...", "details": ... } }`

### POST /accounts
Body: `{ "name": "Alice" }` → **201** `{ id, name, balance: 0, created_at }`
- 400 if name is missing/blank, or if the client sends `balance`.

### POST /accounts/:id/transactions
Body: `{ "type": "credit"|"debit", "amount": 50, "description": "...", "reference_id": "abc-1" }`
→ **201** `{ transaction: {...}, balance }`
- 400 invalid type / amount (must be a number > 0, max 2 decimals) / missing reference_id / bad JSON
- 404 `ACCOUNT_NOT_FOUND`
- 422 `INSUFFICIENT_BALANCE` (nothing is saved)
- 409 `DUPLICATE_TRANSACTION` (same reference_id on same account; nothing changes; `details` holds the existing transaction and current balance)

### GET /accounts/:id/balance
→ 200 `{ account_id, balance }`, or 404.

### GET /accounts/:id/transactions?type=&page=&limit=
- `type`: `credit` | `debit` (omit for both)
- `page` (default 1), `limit` (default 10, max 100)
- Newest first.
→ 200 `{ data: [...], pagination: { page, limit, total, total_pages } }`
- 400 on invalid parameters, 404 for unknown account.

### PUT / PATCH / DELETE /accounts/:id/transactions/:txId
→ 405 `IMMUTABLE_TRANSACTION`. Transactions can never be changed.

### POST /transfers (bonus)
Body: `{ "from_account_id", "to_account_id", "amount", "description", "reference_id" }`
→ 201 with both sides' new balances and transactions.
- Debit and credit happen in one database transaction: if anything fails, nothing is saved.
- Errors: 400 (same account / bad data), 404 (an account missing), 422 (insufficient funds), 409 (reference_id already used on either account).

## How data integrity is enforced

- **Atomicity**: each write runs inside one SQLite transaction (`BEGIN IMMEDIATE`). The transaction row and the balance update commit together or not at all.
- **No double spending**: `BEGIN IMMEDIATE` takes the write lock first, so two requests can't read the same balance.
- **Duplicates**: `UNIQUE(account_id, reference_id)` in the database.
- **Immutability**: database triggers reject any UPDATE or DELETE on `transactions`, and the API returns 405.
- **Never negative**: `CHECK (balance >= 0)`; also `CHECK (amount > 0)` and `CHECK (type IN ('credit','debit'))`.
- **Exact money**: stored as integer cents.

## Assumptions

- A single currency; amounts have at most 2 decimal places.
- Duplicate `reference_id` returns **409** (not 200), with the original transaction in `details`. The payload isn't compared; the first one wins.
- Ids are UUIDs generated by the server.
- Transfers use the same `reference_id` on both accounts (allowed, since it's unique per account).
- No authentication, since it wasn't requested.
- Accounts can't be deleted or renamed (not requested).
- Timestamps are ISO-8601 UTC. Ties in `created_at` are broken by an insertion counter so ordering is stable.
